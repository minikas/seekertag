# SKR integration review

> Registro anterior ao compromisso v2. O comportamento atual e as verificações estão no [relatório v2](skr-commitment-review.md); consulte também o [ABI atual](skr-protocol.md). Artefatos de teste podem ter sido atualizados pela execução v2.

Review date: September 16, 2026. Scope: the working-tree API, browser/native transaction boundary, local-validator and browser test harnesses, and container packaging. This reviewer implemented the escrow contract and protocol SDK; the review is independent of the API, UI and harness implementations, not an independent audit of the reviewer's own contract. A separate team member reviewed contract security.

This document records source findings and remediation, not a production certification. No mainnet deployment or real-fund transaction was performed. Local-validator execution and browser results are recorded separately by the coordinator.

## Integration findings

| Finding | Impact and trigger | Source status at review |
| --- | --- | --- |
| I-01: prefunded receipt address rejected by the API | Sending SOL to a publicly visible draft receipt PDA made reconciliation fail, even though the contract supports initializing prefunded system accounts. This could prevent the owner from preparing the deposit. | Fixed: [reward-chain.js](../server/reward-chain.js) treats a nonexecutable, empty, system-owned receipt address as uninitialized only while the database reward is a draft. Existing funded/terminal rows still reject missing or substituted receipts. Regression coverage is in [rewards.test.js](../server/test/rewards.test.js). |
| I-02: public reads could starve settlement | Each unauthenticated scan joined the same serial queue as owner payments and refunds. Many scans during slow RPC responses could put owner operations behind a long queue of identical reads. | Fixed: [rewards.js](../server/rewards.js) coalesces concurrent read reconciliation per reward into one promise. Authentication, RPC verification and mutation serialization remain in place. Regression coverage exercises concurrent public requests. |
| I-03: payout preparation lost the verified recipient | The UI requested a sync before preparing payment, but the sync response contained only the reward. The following recipient check always failed because the verified recipient was absent. | Fixed: report sync endpoints now return the full conversation reward envelope, including the verified recipient, opaque report reference and resolution eligibility. [Rewards.tsx](../src/Rewards.tsx) binds the expected recipient and reference; [reward-transaction.ts](../src/reward-transaction.ts) checks both when rebuilding the exact permitted message. |
| I-04: RPC outage looked like an intentionally disabled feature | A failed network check returned `enabled: false`; the UI could hide an existing deposit and enable its normal return control. The API still rejected unsafe resolution, but the displayed state was misleading. | Fixed: configured but unreachable deployments return `enabled: true, available: false`. The UI still fetches historical reward state even when new deposits are disabled, preserves an unavailable receipt view and relies on verified `canResolve`. No failed network response is accepted as payment evidence. |
| I-05: runtime network downgrade weakened mint checks | The browser wallet adapter uses the wallet's selected network. Previously, runtime configuration controlled whether the frontend required the official SKR mint. A compromised or incorrectly configured API could label a transaction as a test network while supplying a different network's blockhash and asset. | Fixed in the transaction boundary: [reward-transaction.ts](../src/reward-transaction.ts) requires build-time cluster, program and mint pins to match the API configuration. Mainnet additionally requires the official SKR mint, and test deployments reject that mint. The browser adapter still does not programmatically switch the wallet's selected network; an honest mismatch can fail to submit. Deployment builds must provide all three pins. |

## Harness and packaging findings

| Finding | Impact | Remediation / execution status |
| --- | --- | --- |
| H-01: browser server initialized before export existed | `startRewardFixture({ webDistPath })` ran before Expo created that directory and `index.html`. Since the server validates its static root at construction, a clean run failed immediately; a repeated run could depend on stale files. | Fixed in source: the fixture now reserves its origin, invokes an awaited `prepareWeb` callback with the ephemeral deployment configuration, and only then constructs the static-serving application. Runtime passed in the coordinator browser run. |
| H-02: Docker browser build omitted deployment pins | `.env*` is excluded from the build context, and the build stage initially accepted no `EXPO_PUBLIC_SKR_*` arguments. The new mandatory frontend pins would therefore be absent from the resulting browser bundle even if server-side rewards were enabled at runtime. | Fixed in source: the web build stage now accepts arguments for cluster, program, mint and application origin. Server runtime variables cannot change values already embedded in an Expo export. Deployment documentation and container execution remain coordinator responsibilities. |
| H-03: validator shutdown could await an exit event twice | A process killed by a signal can have `exitCode === null` with a non-null `signalCode`. Testing `exitCode` alone after SIGTERM could attempt SIGKILL on an exited child and wait forever for another exit event. | Fixed in source: the harness tests both exit fields, registers the exit promise before signaling, reuses that promise, bounds both termination waits, and closes its test RPC websocket. |
| H-04: generic rejection assertions could accept transport failures | Bare `assert.rejects` considered any RPC, serialization or timeout failure a successful security rejection. State assertions catch persistent outages but do not prove that each attempted attack reached and was rejected by the escrow program. | Fixed in source: [reward-test-assertions.mjs](../scripts/reward-test-assertions.mjs) requires `SendTransactionError` and logs identifying this program's failure. The escrow suite uses it for negative cases, missing signature and losing race results. Per-error-code assertions would be additional precision; unrelated transport/signing failures can no longer pass these checks. |
| H-05: validator defaults could read the user's CLI configuration | The installed validator documents a default user configuration file and a genesis mint derived from the client keypair. Omitting explicit overrides weakened the harness's claim that it never reads existing wallets. | Fixed in source: the validator receives a dedicated temporary CLI configuration, an explicit unused test genesis mint address and a loopback URL. It does not fall back to the user's configured wallet or RPC. |

The rent-squatting scenario was corrected during review to prefund the addresses with the zero-data account rent minimum. A separate transaction containing a one-lamport transfer to a nonexistent address can be rejected by runtime rent rules before the escrow is exercised.

The production container installs the API's runtime dependencies and exposes them to the shared SDK through a root `node_modules` symlink, includes `shared/`, serves the exported browser build and runs as the `node` user. Source layout is consistent with ESM package resolution. This source review does not claim that the Docker image has been built or smoke-tested.

## Test validity and boundaries

The local tests create an isolated validator, ephemeral application signing keys and a six-decimal test mint; no remote RPC is accepted by the harness. The validator's CLI configuration is isolated from existing wallets. Positive tests assert actual SPL balances and decoded program-owned receipts, so they are stronger than a mock-only lifecycle test. The API integration also checks exact payout amount, signature verification, authorization, replay rejection, unchanged QR URL and report-specific return gating.

The browser harness replaces only the external wallet provider. Signing keys remain in the Node test process; the application, HTTP API, database and SBF program are real. Browser success would validate this simulated-provider boundary, not Phantom/Solflare behavior or a physical Android Mobile Wallet Adapter session. It captures API response failures, browser exceptions, request timings and mobile overflow; recording timings alone is not a performance budget assertion.

The owner's release authority is an explicit economic limitation: the owner can call the contract directly and pay a wallet they control before expiry. The expiry condition restricts the refund instruction, and the protocol cannot establish physical handover or distinct human identity. Product and protocol wording must describe a currently deposited balance and owner-authorized payout, not unconditional retention until expiry or guaranteed payment to an honest finder. The escrow integration test includes a direct owner-controlled recipient demonstration.
